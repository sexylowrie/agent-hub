Claude Code / Codex / Cursor 远程控制原理与统一管理方案

整理日期 2026-09-23 · 基于官方文档、开源仓库与本机实测 · 本机环境 macOS，Claude Code 2.1.280，ChatGPT App 内置 Codex 0.155，Cursor CLI 2026.03.25

结论。三家的官方 Remote Control 都是同一种形态：本机进程主动出站连接厂商中继，手机端只能用厂商自家 App 接入，中继不对第三方开放。所以走官方路线必须装三个 App。
但三家在本机都留了可编程接口，且已在这台 Mac 上验证可用。把这一层统一封装成一个自建 Hub，用飞书机器人当唯一手机入口，就能一个入口管三家。

一、三家 Remote Control 是怎么实现的

1. 共同骨架

三家都没有让本机开端口，也没有做 NAT 穿透。做法是本机进程主动出站连接厂商中继，手机端也出站连接同一个中继，中继在两条连接之间转发。手机端只发指令和审批结果，代码、文件、凭据留在本机。

3. 为什么官方路线绕不开三个 App

  • 三家中继只认自家客户端，没有公开的"接管某个远控会话"的 REST 接口或 SDK。
  • Claude 的隐藏参数 --sdk-url 是内部协议入口，已加 hostname 白名单；社区自建 relay 靠 patch 二进制，不可依赖。
  • Codex 的 relay 只允许 ChatGPT 客户端配对；exec-server --remote 是让云端任务借用本机执行，方向相反。
  • Cursor 的 Slack / GitHub / Linear 集成只能驱动 Cloud Agent，控制不了本机会话。

二、统一方案：自建本机 Agent Hub，飞书做唯一手机入口

放弃三家的中继，只保留它们在本机的可编程接口。由自己的 Hub 统一封装，手机端只用飞书。飞书机器人用长连接收事件，同样是出站连接，本机依旧不开端口。

2. 统一事件模型

三家事件归一到六种，落 SQLite，每条带厂商原始 session id，随时能回到原生 CLI 继续。

session.created

厂商、工作目录、原始 id、飞书话题 id

user.message

来自飞书的文本，含 steer 中途插话

assistant.delta

流式文本，合并后按段落刷卡片

tool.call

开始 / 结束、命令、改动文件列表

approval.request

类型、风险摘要、超时；对应卡片按钮

turn.done

结果摘要、耗时、diff 统计、下一步建议

4. 飞书侧的使用约定

  • 一个机器人，三个话题群分别对应三家，也可以在一个群里用前缀路由：/cc Claude、/cx Codex、/cu Cursor。
  • 首条消息带工作目录，如 /cc ~/AiProject/my-service 把订单模块补上单测；后续消息自动接到该话题的会话。
  • 流式输出按段落合并刷卡片，避免刷屏；回合结束发摘要卡片，带"看 diff"链接跳到只读 Web。
  • 斜杠命令白名单：/stop 中断、/model、/effort、/new 开新会话、/ls 列会话。

三、本机实测结论（2026-09-23 晚）

围绕三个核心诉求逐家验证：展示会话列表、看进度、桌面端空闲后在手机上接着聊。全部不依赖实时接管 GUI 进程。

Desktop 端拉起 Claude Code 用的正是 --input-format stream-json --output-format stream-json --permission-prompt-tool stdio，与 Hub 计划采用的驱动方式一致，说明这条协议是官方自己在用的稳定路径。

放弃的路线。实时接管 GUI 正在跑的会话，三家都没有正规缝隙：Claude Desktop 与 Codex 的子进程都是 stdio 独占，Cursor 只能靠 Chrome DevTools 协议抓 DOM。诉求里不要求同步，所以 Hub 只做"读存储 + 空闲后续接"。

四、取舍与风险

  • 放弃原生体验。Claude App 的移动端 diff 视图、Cursor 云端并行多 agent 与远程桌面，这些 Hub 不提供。
  • Cursor 这路变成"远程驱动本机 CLI"。与官方云端 loop 不同，本机断网就停；且 agent -p 没有中途审批，必须 sandbox 或 --force 加 worktree 兜底。
  • Claude 长驻流模式下仅终端 UI 的斜杠命令用不了，模型与 effort 走参数；bypass 模式等于把审批交给沙箱。
  • Codex app-server 官方标注 experimental，协议可能变化，靠导出的 schema 做兼容层。codex mcp-server 已被官方移除，不要走那条路。
  • 安全边界。飞书机器人必须限制发送者 open_id 白名单；只读 Web 只走 Tailscale，不上公网。

更省事的替代

开源项目 Happy Coder 宣称一个 App 同时接管 Claude Code 与 Codex 且端到端加密。本轮未验证它 2026 年的兼容状态，也不支持 Cursor。如果它两家可用，只需自己补 Cursor 一路，代价是多装一个 App。
