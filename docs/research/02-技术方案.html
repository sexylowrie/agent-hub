Agent Hub 技术方案

2026-09-23 · 目标：一个入口管 Claude Code / Codex / Cursor 三家本机会话 · 诉求：会话列表、看进度、桌面端空闲后手机续聊 · 前置调研见《三家Agent统一远程管理方案》

选型结论：TypeScript + Node 24，单进程，零原生依赖，手机端先做 PWA。
三家 CLI 本身都是 Node 程序，官方 SDK 与协议类型都是 TypeScript 优先；Hub 的核心工作是处理 NDJSON 流和 WebSocket，这是 Node 的主场；同一门语言同时覆盖后端、Web 端和后续的手机端，迭代不用切上下文。Node 24 内置 SQLite，不需要编译原生模块。

一、语言选型

候选优势劣势结论
TypeScript / Node 24三家 CLI 是 Node 程序，Claude Agent SDK、Codex SDK、Codex app-server 类型绑定全是 TS；流式 JSON 与 WebSocket 生态最成熟；前后端同语言，PWA 可直接复用类型；内置 SQLite 与 WebSocket 客户端类型体操容易过度；需要克制依赖数量采用
Python有现成经验；脚本化快；Codex 有 Python SDKWeb/PWA 要另起一门语言；异步子进程流处理不如 Node 顺手；Claude SDK 的 TS 版更新更快备选
Java / Kotlin你的主力语言；工程规范成熟启动重、单人小项目迭代慢；处理 NDJSON 子进程流样板代码多；没有三家 SDK不采用
Go单二进制分发、常驻进程稳没有三家 SDK，协议类型要手写；前端仍需另一门语言；目前不需要分发给别人不采用

二、总体架构

关键设计决定

  • 读与写分离。会话列表和进度靠 Scanner 只读三家存储，不起任何 CLI 进程；只有用户从手机发消息时，Adapter 才拉起一个续接进程。桌面端在工作时 Hub 完全不干扰它。
  • 空闲判定由 Scanner 负责。Claude 看 jsonl 最后一条是否为 result 且无新写入；Codex 看 GUI 子进程是否有活跃 turn，简化为 jsonl 静默超过阈值；Cursor 看 generatingBubbleIds 是否为空。非空闲时手机端"续聊"按钮置灰，避免两个进程同时写一个会话。
  • Adapter 一次一轮。手机发一句，Adapter 起进程、跑完一轮、退出。不维持长驻子进程，重连、崩溃恢复都简化为"下一轮重新 resume"。Claude 和 Cursor 天然如此；Codex 用 app-server 时也在 turn 结束后关闭。
  • 事件先落库再广播。客户端断线重连按序号补拉，手机弱网不丢消息。

表关键字段说明

统一事件类型

type HubEvent =
  | { type: 'session.upsert';   session: SessionView }             // Scanner 发现或更新
  | { type: 'session.state';    sessionId; state: SessionState }   // idle / running / awaiting_approval / error
  | { type: 'turn.started';     sessionId; turnId; source: 'desktop' | 'hub' }
  | { type: 'message.user';     sessionId; turnId; text }
  | { type: 'message.delta';    sessionId; turnId; text }          // 流式增量，客户端合并
  | { type: 'tool.call';        sessionId; turnId; name; input; status: 'started' | 'done'; output? }
  | { type: 'approval.request'; sessionId; turnId; approvalId; kind; summary; expiresAt }
  | { type: 'approval.decided'; approvalId; decision: 'allow' | 'deny' | 'allow_session'; by }
  | { type: 'turn.done';        sessionId; turnId; result; usage?; durationMs }
  | { type: 'error';            sessionId?; message; recoverable }

五、Adapter 接口与三家实现要点

interface AgentAdapter {
  readonly vendor: 'claude' | 'codex' | 'cursor'
  // 在已有会话上跑一轮；返回 AsyncIterable，产出统一事件；结束即进程退出
  resume(session: SessionRef, input: string, opts: RunOpts): AsyncIterable<HubEvent>
  // 新会话
  start(cwd: string, input: string, opts: RunOpts): AsyncIterable<HubEvent>
  // 审批回执；由 Core 在收到客户端决定后调用
  answerApproval(approvalId: string, decision: Decision): Promise<void>
  interrupt(sessionId: string): Promise<void>
}
产品拉起方式事件映射审批已验证
Claudeclaude -p --resume <id> --input-format stream-json --output-format stream-json --include-partial-messages --permission-prompt-tool stdio，与 Desktop 拉起方式一致assistant/content_block_delta → message.delta；tool_use / tool_result → tool.call；result → turn.donestdin 收 control_request(can_use_tool)，回 control_responseresume 成功
Codexspawn codex app-server（stdio），initialize → thread/resume → turn/start；归档先 thread/unarchiveitem/* 通知 → message.delta / tool.call；turn/completed → turn.done服务端请求 item/*/requestApproval，回 accept / decline / acceptForSessionthread/list、resume 成功
Cursoragent -p --resume <composerId> --output-format stream-jsonassistant → message.delta；tool_call started/completed → tool.call；result → turn.done无中途审批。默认 --sandbox enabled；用户在手机上显式选择"放行"才加 --forceresume 成功，上下文完整
Cursor 的已知偏差。CLI 续聊的内容写在 ~/.cursor/chats，IDE 数据库不回写。Scanner 对 Cursor 要同时读两处并按 composerId 合并，手机上看到的是完整对话，IDE 窗口里看不到手机那几句。

六、Scanner：只读三家存储

产品列表来源进度来源空闲判定注意
Claude遍历 ~/.claude/projects/*/*.jsonl，首行取 cwd、entrypoint、sessionId；跳过 subagents 目录与 sidechaintail 文件增量解析最后一条为 result 且 3 秒无写入过滤 entrypoint 为 sdk-cli 的内部工具会话
Codexstate_5.sqlite threads 表（只读打开，immutable=1 避免锁）rollout_path 指向的 jsonl tailjsonl 5 秒无写入rollout_path 不存在 → resumable=false；archived=1 → 续接前 unarchive
Cursorstate.vscdb 中 composerData:* 键；库有 10GB，只按 key 点查，不全表扫bubbleId:<composer>:<id> 按 fullConversationHeadersOnly 顺序取generatingBubbleIds 为空且 status 非 generatingWAL 模式，只读连接需带 ?mode=ro；合并 ~/.cursor/chats 的 CLI 续聊

fs.watch 触发增量，每 60 秒全量对账一次兜底。首次启动只扫最近 30 天，历史会话按需分页加载。

设备配对流程

网络

  • 第一阶段只走 Tailscale。Hub 监听 tailnet 地址，手机装 Tailscale 后 PWA 直连，网络层已带设备身份，Hub 的 token 是第二道。不开公网端口，不做 relay。
  • Web Push 需要 HTTPS。用 Tailscale 自带的证书签发给 Hub，PWA 才能注册推送。iOS 要求 PWA 添加到主屏幕后才收推送。
  • relay 留到第三阶段，等出现"没有 Tailscale 的手机也要用"这个需求再做。

八、PWA 界面

会话列表页

按更新时间排序，每行显示厂商色条、标题、目录、状态（运行中 / 空闲 / 待审批）、最后一句摘要。运行中的行有进度条式的实时更新。不可续接的灰显并标注原因。

会话详情页

消息流 + 工具调用折叠块 + 审批卡片。底部输入框，会话运行中时禁用并显示"桌面端正在工作"。Cursor 会话多一个"放行执行"开关。

审批卡片

命令或文件改动摘要、目录、风险标签、三个按钮：允许 / 拒绝 / 本会话允许。倒计时显示到期时间。

新建会话

选厂商、选目录（配置文件里的白名单）、输入首句。

九、常驻与可靠性

  • launchd 用户级 agent，KeepAlive，崩溃自动拉起；日志按天写到 ~/Library/Logs/agent-hub/。
  • Hub 起来时对每个未完成的 Hub 发起的轮次做一次对账：进程不在了就标记 error，让用户重发。
  • caffeinate -s 由 Hub 按需调用：有运行中的 Hub 轮次时阻止休眠，空闲时释放，不常年防休眠。
  • 三家二进制路径写在配置里并在启动时校验版本；Codex 版本变化时提示重新生成协议类型。
  • 并发保护：同一会话同一时间只允许一个 Hub 轮次；Scanner 判定非空闲时拒绝 send 并返回原因。
